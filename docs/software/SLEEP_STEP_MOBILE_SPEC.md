# Sleep and step algorithms: Android / iOS integration specification

**Status: specification only.** No mobile code exists in this repository (`mobile_app/` is empty) and nothing here
was built, run or tested on Android, iOS, a simulator or a phone. The Python implementation is the reference;
a port is correct only if it reproduces `tests/regression/sleep_step_vectors.json`. Do not describe a port as
validated on hardware until it has run on a physical device.

## 1. What a port must implement

| Component | Reference | Streaming? | Notes |
|---|---|---|---|
| Epoch features (5 s sub-epoch means → Δz, Δg, ENMO, SD, coverage) | `parkinsense/sleep/features.py` | batch per night; incremental form possible with `last_sub_vector` | float64; epoch grid starts at the first sample time `t0` |
| Context features + logistic regression | `sleep/model.py`, weights `sleep/params.py` | batch (needs ± 5 min context and "until next movement": the latter is non-causal) | A live-sleep display would need a causal variant and **new validation** |
| Night summary | `sleep/night.py` | batch | thresholds are constants in the file |
| Production step counter v1.1 | `activity/step_counter.py` | per sample | default |
| Gated step counter 3.0-dev | `activity/step_counter_v2.py` | per sample, FFT every 0.5 s | opt-in only |

The weights file is the model: 6 weights, 1 bias, threshold 0.7. No library is needed beyond an FFT (gated steps)
and a 4th-order Butterworth band-pass design (SOS coefficients for fs = 104 Hz can be exported from
`scipy.signal.butter(4, [0.5, 3.5], 'bandpass', fs=104, output='sos')`; ports should embed the exported
coefficients, not redesign them).

## 2. Parity tests

`tests/regression/sleep_step_vectors.json` (generated by `python tests/regression/make_sleep_step_vectors.py`):

| Block | Input | Expected | Tolerance |
|---|---|---|---|
| `sleep` | 4 Hz synthetic acceleration, 40 min | dg_max, dz_max, enmo, 6 features per epoch, P(sleep), state | 1e-5 absolute; states identical |
| `night` | epoch table, 5 h | night summary fields | numbers equal to the stored rounding; strings equal |
| `steps` | 104 Hz synthetic walking, 40 s, motion state ACTIVE | total steps, event times (default and gated) | counts identical; times ± 1 ms |

A port's CI must load this file and assert all three. The Python side asserts that the reference still reproduces the file
(`tests/regression/test_sleep_step_vectors.py`); regenerating the file is a deliberate act that changes the algorithm
version policy below.

## 3. Behaviour that must match, not just numbers

* Gap handling: an epoch with < 50 % of expected samples is NaN/−1, never interpolated. A sub-epoch with < 25 % is NaN.
* `INSUFFICIENT_DATA` returns **no** summary numbers; every summary carries `estimate = true`.
* No sleep stages in any API, screen or export. The label "sleep efficiency" must not be used for `period_efficiency`.
* Display text must state: movement-derived estimate, not polysomnography, not clinically validated, not validated on
  ParkinSense hardware.
* Timestamps: signal time (device µs, unwrapped), never phone arrival time (the original step counter bug).
* Versions written next to every result: `sleep_algorithm_version`, `step_algorithm`, `step_algorithm_version`,
  pipeline version, firmware version.

## 4. Platform constraints (not tested)

* **Background execution.** Overnight BLE streaming needs a foreground service (Android) or `bluetooth-central`
  background mode (iOS), with OS-specific limits; neither was tried. The firmware currently stops streaming without finger
  contact (`docs/hardware/SLEEP_STEP_HARDWARE_LIMITS.md`) — an overnight recording is impossible until that is addressed.
* **Storage.** 8 h at 104 Hz is about 3 M samples; store raw acceleration (not only results) so analyses can be re-run
  when the algorithm version changes.
* **Run sleep analysis offline** after the night (first-wake to final-wake is non-causal), not during streaming.

## 5. Version policy for ports

A port declares the reference commit and `SLEEP_ALGORITHM_VERSION` it matches. A change to features, weights, thresholds
or the night rules bumps that version, regenerates the vectors, and records an ADR. Historical results are not
recomputed silently.
