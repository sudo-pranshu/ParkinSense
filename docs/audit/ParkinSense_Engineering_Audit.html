ParkinSense

Independent Engineering Audit — Python Runtime, DSP Pipelines & nRF52840 Firmware

Prepared for Pranshu Kumar  ·  Branch develop  ·  7 August 2026  ·  Report only — no code was modified

1. Executive Summary

ParkinSense is a genuinely ambitious piece of engineering. The module boundaries are sensible, the naming is disciplined, and ppg/algorithms.py in particular contains signal-processing work that is well above the level normally seen in an undergraduate or hobbyist wearable project — the ratio-of-ratios derivation, the beat-morphology scorer, and the lock state machine are all carefully reasoned and unusually well documented.

The problem is that most of that quality lives in modules that the running system either does not reach, or reaches under conditions that invalidate their assumptions. This audit found four defects severe enough to mean that several headline biomarkers are unlikely to be producing correct values on real hardware today, plus a broad class of documentation claims that the code does not support.

The good news is that the four critical defects are all narrow and localised. None of them require architectural redesign. Three are configuration or call-site mistakes fixable in under fifty lines; the fourth is a scheduling change in one function.

The four critical findings

  1. The entire analysis pipeline executes once per sample (104 Hz), not once per window. Every stateful temporal component in the system — the hysteresis state machine, the persistence counters, the PPG finger debounce, the HR outlier hold — was designed around one call per analysis window and is receiving roughly 104 calls per second instead. Their time constants are therefore wrong by a factor of ~400, and the CPU cost is roughly two orders of magnitude higher than necessary.
  2. The PPG sample-rate contract is broken at three points in a row. The firmware delivers ~10 unique PPG samples per second, zero-order-holds them into 104 Hz packet slots, and the runtime then tells PPGProcessor the rate is 50 Hz. The arithmetic predicts that heart rate returns None for any true resting rate below about 94 BPM — which is exactly the symptom the README's own troubleshooting table documents as a user error.
  3. Gyroscope and accelerometer samples can silently overflow int16 on the wire. The IMU range settings are assigned after imu.begin() and therefore never applied, so the sensor runs at ±2000 dps / ±16 g while the packing arithmetic assumes ±250 dps / ±4 g. Ordinary voluntary wrist motion exceeds 250 dps and wraps around — injecting large false transients into the primary tremor signal.
  4. The advertised deep-sleep state does not sleep. There is no power-management call of any kind in the firmware. The "sleep" path is a delay(10); return; loop with BLE still advertising and the MAX30102 LEDs still driven. The microamp figure in the README is not achievable from this code.
Framing for the paper. The most valuable thing in this audit is not the bug list — it is that several claims in the README describe modules that exist but are not reached by the running system (the temporal validator, the tremor state machine, motion-aware PPG confidence, the advanced PPG peak detector). An IEEE reviewer who reads the repository alongside the paper will find these. Section 7 tabulates them so they can be either wired up or reworded before submission.

3. Architecture — As Built

3.1 What is actually in this branch

The README documents a repository layout that this branch does not have. Confirmed present: dashboard/python/ (49 Python files), firmware/xiao_nrf52840/src/ (6 sketch directories), tests/ (6 files), docs/SRS/, data/metadata/, .github/workflows/.

Confirmed absent: Android/, hardware/, research/, docs/images/ (every image the README embeds is a broken link), LICENSE (the README says "See the LICENSE file"), and the two firmware directories the Getting Started section instructs the reader to open — the actual directories are parksense_ble_stream_v3/, parksense_wearable_v3/ and parksense_ble_stream_optimized_v4/.

Anyone following the README's setup instructions on a fresh clone of develop will fail at the firmware step and again at the Android step. This is the first thing a reviewer or a prospective contributor will encounter.

Two observations from the map itself. First, the file-based decoupling between runtime and dashboard is a genuinely good decision and should be kept — it is what makes replay and offline validation possible. Second, everything inside MotionPipeline.process() is stateless recomputation over a 4-second window, invoked 104 times per second on a window that has advanced by one sample. That single fact drives most of what follows.

4. Critical Findings (P0)

P0-1 The whole pipeline runs per-sample, invalidating every temporal component

runtime_v2.py:185–257 · state_machine.py:21–61 · temporal.py:13–37 · ppg_processor.py:144–151

The decode loop iterates the ten samples in each packet, and the guard that gates analysis sits inside that loop:

for i in range(BATCH_SIZE):                     # runtime_v2.py:185
    ...
    if len(gx_buffer) == WINDOW_SIZE:           # runtime_v2.py:224
        result = pipeline.process(...)          # runtime_v2.py:225

Because gx_buffer is a deque(maxlen=416), once it has filled it stays full forever. The condition is true for every subsequent sample, so the full pipeline runs 104 times per second on a window that has advanced by a single sample — a 99.76% overlap between consecutive analyses.

Consequence 1 — every temporal design is degenerate. TremorStateMachine requires high_count >= 2 to leave NO_TREMOR and >= 4 to reach CONFIRMED. Those were clearly intended as "2 windows" and "4 windows" — 8 s and 16 s of evidence. At 104 calls/s they are 19 ms and 38 ms. The hysteresis the README presents as a core false-positive defence provides essentially no temporal filtering. The same applies to the PPG finger debounce and the HR outlier hold.

Consequence 2 — a latent lock-up in the state machine. Scores strictly between LOW=55 and HIGH=75 increment neither counter (state_machine.py:26–34). A score that settles at, say, 65 leaves both counters frozen at their last values, and the state never advances or decays. There is no timeout and no decay path. A session can sit in CONFIRMED_TREMOR indefinitely on a signal that no longer qualifies.

Consequence 3 — cost. Each call performs 9 filtfilt passes over 416 samples, 3 Welch PSDs, and a full PPG chain including 3–4 FFTs over 500 samples. Multiplied by 104/s this is roughly 100× more work than the analysis actually requires, on top of 104 JSON file rewrites and 104 fsync-inducing CSV flushes per second.

Recommended direction. Introduce a hop counter and analyse every N samples — N = 52 gives 2 Hz analysis with 50% window overlap, which is conventional for this kind of detector and preserves the temporal constants' intended meaning. Everything downstream then behaves as designed without touching any algorithm. This one change is the highest-leverage fix in the report.

P0-2 PPG sample-rate contract is broken at three consecutive stages

parksense_ble_stream_v4.ino:114, 265–276, 328–329 · motion_pipeline.py:38 · ppg_processor.py:124–132 · algorithms.py:1817

Three independent rate assumptions disagree, and they compound.

Stage 1 — the firmware decimates 100 SPS to 10 Hz by discarding. The MAX30102 is configured at 100 samples/second (setup(0x1F, 1, 2, 100, 411, 4096), line 114). The PPG block runs on a 100 ms tick and drains the whole FIFO, but assigns rather than accumulates:

if (spo2Ready && (nowMs - lastPPGMs) >= 100) {   // line 265
    max30102.check();
    while (max30102.available()) {
        latestIR  = max30102.getFIFOIR();          // overwritten each iteration
        latestRED = max30102.getFIFORed();
        max30102.nextSample();
    }
}

Roughly ten samples accumulate per tick and nine are thrown away. The effective PPG rate reaching the host is 10 Hz — the code comment at line 80 says so explicitly ("runs at 10 Hz"), while the README states ~50 Hz throughout.

Stage 2 — zero-order hold into 104 Hz slots. Lines 328–329 write latestIR/latestRED into every IMU sample slot, so each unique PPG value is repeated about 10.4 times. A 500-sample buffer therefore contains roughly 48 distinct measurements, not 500.

Stage 3 — the runtime declares the wrong rate. MotionPipeline.__init__ constructs PPGProcessor() with no arguments (motion_pipeline.py:38), taking the defaults sample_rate=50, window_seconds=10. But samples arrive at 104 Hz. So the "10-second" window is really 4.8 s, and — critically — every conversion from samples to seconds is wrong by a factor of 104/50 = 2.08.

The arithmetic. Heart rate is derived at algorithms.py:1817 as rr_raw = np.diff(peaks) / fs with fs=50. For a true 70 BPM the beat spacing is 0.857 s = 89 samples at the real 104 Hz, which the code reads as 89/50 = 1.78 s. The physiological-bounds filter at line 1819 accepts only 0.333–1.333 s, so every interval is rejected, rr.size < 2, and the function returns heart_rate: None.

Working the bound backwards: a value is reportable only when the true rate is between roughly 94 and 374 BPM, and it then reads about 48% of the true rate. That is precisely the behaviour the README's troubleshooting table records as user error — "Heart Rate stuck near None: hold still for the full 10 s buffer to fill" and "HRV always None". This is not a contact problem; the arithmetic cannot produce a resting heart rate.

Prediction, not observation — verify in about two minutes: log len(self._ir_buffer) and the hr_debug trace (process(..., debug=True) already exposes it) during a normal finger-on capture and check whether rr_ms_before_filtering clusters near 1800 ms rather than 850 ms. Also note that the README's sample output showing 71.4 BPM would require a true rate of ~148 BPM under this analysis.

Recommended direction. Three separable fixes: (a) accumulate the FIFO in the firmware instead of overwriting, and send the real PPG rate; (b) decide on one canonical PPG rate and pass it explicitly — PPGProcessor(sample_rate=<actual>) — rather than relying on a default; (c) add a startup assertion that compares measured arrival rate against the configured fs and refuses to run silently on a mismatch. A single wrong default should not be able to disable a headline biomarker in silence.

P0-3 IMU range settings are never applied; gyro samples overflow int16 during normal motion

parksense_ble_stream_v4.ino:86–102, 315–326 · runtime_v2.py:206–212

The sensor configuration is assigned after the driver has already been initialised:

if (imu.begin() != 0) { ... }
else {
    imu.settings.accelEnabled = 1;
    imu.settings.gyroEnabled  = 1;
    imu.settings.accelRange   = 4;      // never reaches the hardware
    imu.settings.gyroRange    = 245;    // never reaches the hardware
}

In the SparkFun LSM6DS3 driver, begin() is what writes settings into the device registers. Mutating the struct afterwards has no effect. The sensor therefore runs at the library defaults — ±16 g, ±2000 dps, and a 416 Hz output data rate.

Meanwhile the packing arithmetic assumes the intended ranges:

packet.samples[i].gx = (int16_t)(gx_f * 131.0f);   // saturates at ±250 dps
packet.samples[i].ax = (int16_t)(ax_f * 8192.0f);  // saturates at ±4 g

The scale factors round-trip correctly against the host (runtime_v2.py:206–212 divides by the same constants), so quiet data is fine. The problem is the ceiling. 131 × 250 = 32,750, just inside int16. Any gyro reading beyond ±250 dps wraps to the opposite sign. Ordinary voluntary wrist rotation routinely peaks in the 300–800 dps range — reaching for a cup, turning a door handle, gesturing while speaking.

Why this matters for the science. A wrap produces a full-scale sign discontinuity in the gyroscope trace. Fed through a 3–8 Hz band-pass, a step discontinuity rings at the filter's centre frequency — that is, it manufactures energy squarely inside the tremor band from a movement that is not tremor. The tremor detector's most important failure mode is false positives during voluntary motion, and this creates exactly that artefact. The ACTIVE motion-context veto will suppress many of these, but the LOW MOTION band will not.

Secondary effect — IMU aliasing. With settings unapplied, the sensor's ODR is 416 Hz and its internal anti-alias filter is configured for that bandwidth, while the firmware samples it at 104 Hz. Content between 52 Hz and 208 Hz folds down into 0–52 Hz, including into the tremor band. There is no decimation filter anywhere in the chain.

Recommended direction. Populate imu.settings before calling begin(), then either set the ODR to 104 Hz so no decimation is needed, or keep a higher ODR and add a proper decimation filter. Separately, add a saturation check around the int16 cast so that clipping is recorded in the packet flags byte (which is currently always zero) rather than being invisible — for a research platform, knowing a sample was clipped matters as much as the sample.

P0-4 "Deep sleep" is a busy-poll; the microamp claim is not supported by this firmware

parksense_ble_stream_v4.ino:196–227, 279–282 · README "Battery Optimization" and "Performance"

A search across the whole firmware tree for power-management calls — sd_power_system_off, NRF_POWER->SYSTEMOFF, waitForEvent, __WFE, suspendLoop, shutDown, setLEDMode — returns no matches. Not one. The sleep path is:

if (!systemActive) {
    if (spo2Ready && (nowMs - lastFingerCheckMs) >= FINGER_POLL_INTERVAL_MS) {
        ... threshold IR, debounce ...
    }
    delay(10);
    return;
}

In this state the CPU does idle inside delay(), but three things keep drawing current: BLE advertising continues (restartOnDisconnect(true), Advertising.start(0) — never stopped), the MAX30102 keeps running at 100 SPS with both LEDs driven at 0x1F, and the I2C bus is polled four times a second. The MAX30102 alone in this configuration draws on the order of milliamps. Microamp-range current is not reachable from this code path, and consequently neither is the ~100-hour runtime figure derived from it.

The active path has a separate issue. Line 279 returns immediately when the sample interval has not elapsed, so loop() spins at full speed continuously — the Cortex-M4 never enters a wait state between the 104 Hz samples, which is where the bulk of the ~7 mA active figure comes from. On an nRF52840 with the SoftDevice, yielding to sd_app_evt_wait() in that branch is a small change with a large effect.

Recommended direction. In the sleep path: call max30102.shutDown() (or drop to a 1 Hz proximity mode), stop advertising, and use a low-power timer to schedule the finger poll rather than a 10 ms spin. In the active path: yield to the SoftDevice's wait-for-event instead of returning early from loop(). Then re-measure on the Power Profiler Kit and quote the new numbers. Until then, the README's two power figures should be softened, since they are the most falsifiable quantitative claims in the document.

5. High-Priority Findings (P1)

P1-5 Motion-aware PPG confidence — the headline fusion feature — is never invoked

motion_pipeline.py:89–92 · ppg_processor.py:101–106, 177–182, 375

PPGProcessor.process accepts a motion_state argument and applies MOTION_CONFIDENCE_MULTIPLIERS to the HR confidence. The single call site omits it:

ppg = self.ppg.process(ir, red)     # motion_pipeline.py:89 — no motion_state

The multiplier lookup therefore resolves to .get(None, 1.0) — always 1.0, always a no-op. This is the mechanism behind two README claims: "Motion-aware Confidence: HR confidence is discounted according to the Motion Pipeline's reported activity state," and the Cross-Pipeline Fusion bullet "Motion context reduces confidence in PPG estimates during heavy movement."

There is a second defect hiding behind the first. Even once the argument is passed, the dictionary keys are "LOW_MOTION" with an underscore (ppg_processor.py:103), while MotionContext emits "LOW MOTION" with a space (motion_context.py:41). The lookup would miss and fall through to 1.0. This is the identical failure mode that StepCounter's comment at lines 279–285 records as having been diagnosed and fixed once already — string-keyed cross-module contracts are silently failing in more than one place.

Recommended direction. Pass the state through, and replace the raw strings with an enum or module-level constants shared by producer and consumer so a mismatch becomes an import error rather than a silent 1.0.

P1-6 The temporal validator is dead code; the state machine's output is discarded

temporal.py (whole file) · rule_engine.py:49–55 · runtime_v2.py:263–267

The README describes a "Temporal Validator — requires 5 positive windows out of a rolling 10 before confirming tremor." That is TemporalSmoother in detector/temporal.py, and an import-graph search finds exactly one importer: tests/test_temporal.py. It is never constructed in the runtime. No 5-of-10 validation occurs anywhere in the live path.

The state machine fares slightly better but ends the same way. RuleInferenceEngine does call it and stores the result — detector["state"] = self.state_machine.update(...) — but the runtime never reads that key. The published classification comes from a different quantity entirely:

"classification": "TREMOR" if analysis["tremor"] else "NO TREMOR"   # runtime_v2.py:263

where analysis["tremor"] is the raw score >= 80 test from multiaxis_detector.py:96. So the system publishes an instantaneous threshold crossing, computes hysteresis alongside it, and throws the hysteresis away. Three separate thresholds coexist — 80 for the boolean, 75 and 55 for the state machine — with only the first having any effect.

Recommended direction. Decide which is authoritative. If the state machine is meant to be the output (it should be — that is the whole point of hysteresis in a clinical-adjacent detector), publish CONFIRMED_TREMOR as the classification and demote the raw boolean to a diagnostic field. Then either wire TemporalSmoother in or delete it and remove the claim.

P1-7 PPG decimation without an anti-aliasing filter corrupts the SQI harmonic ratio

parksense_ble_stream_v4.ino:269–274 · algorithms.py:811–824

Reducing 100 SPS to 10 Hz by keeping the newest FIFO sample is decimation without a low-pass stage — a textbook aliasing violation. Everything above the new 5 Hz Nyquist folds back into the band below it, including motion transients and LED-driver ripple, landing directly on top of the cardiac band.

The concrete casualty is harmonic_ratio, one of the six components of the Signal Quality Index. It integrates power at 2f₀ and 3f₀ (algorithms.py:822–823). For a resting 1.2 Hz fundamental those sit at 2.4 Hz and 3.6 Hz — still below Nyquist. But at 100 BPM (1.67 Hz) the third harmonic is at 5.0 Hz, exactly at Nyquist, and above that it aliases. So the SQI's harmonic term is measuring folded energy for any elevated heart rate, and the SQI feeds HR confidence, sensor status, and the SpO₂ gate.

Recommended direction. Average the FIFO samples in the firmware rather than discarding them — a 10-sample box average is a crude but effective anti-alias filter, costs almost nothing, and improves SNR by roughly √10. Better still, use the MAX30102's own sampleAverage hardware setting (currently 1) to do it in the sensor.

P1-8 Reported tremor frequency is a three-axis mean, inconsistent with the selected best axis

multiaxis_detector.py:39–52, 130 · feature_extractor.py:57–67

The detector picks a best_axis by maximum band ratio, but reports the frequency as an unweighted mean across all three axes:

mean_freq  = np.mean(freqs)                          # line 39
best_axis  = ["gx","gy","gz"][np.argmax(powers)]      # line 45
...
"frequency": mean_freq,                              # line 130 — not the best axis

If tremor is genuinely present on gy at 5.2 Hz while gx and gz carry low-amplitude broadband noise whose spectral peaks land at, say, 3.1 Hz and 7.6 Hz, the reported frequency is 5.3 Hz by coincidence — and with a different noise realisation it could be 4.1 Hz. The value published as "Tremor Frequency — dominant oscillation" is not the dominant oscillation of the axis the system just identified as dominant.

The same statistic drives axis_agreement = 1 - freq_std/2, which contributes 20 points to the score and 25 to the confidence. Because Welch's resolution here is 104/256 = 0.406 Hz, freq_std is quantised in steps of roughly 0.19 Hz, and clearing axis_agreement > 0.85 requires all three axes to land within a single FFT bin. That is a brittle gate on a quantised quantity.

Recommended direction. Report the best axis's own dominant frequency, or a band-power-weighted mean across axes. Compute agreement only over axes whose band ratio clears a floor, so noise axes cannot vote. And apply parabolic interpolation to the PSD peak — three lines of code that recover roughly an order of magnitude of frequency precision and would justify the two-decimal reporting the system already does.

P1-9 Zero-phase filtering applied to a sliding real-time window puts the largest transient on the newest sample

gravity.py:26 · notch.py:34 · bandpass.py:41 · motion_pipeline.py:60–72

All three motion filters use filtfilt, which is non-causal: it filters forwards then backwards, and pads the signal by reflection at both ends. That is the right tool for offline analysis of a complete recording. Applied to a sliding window in real time it has two consequences that matter here.

First, the filter is stateless across calls — each invocation re-pads and re-filters from scratch, so the reflection artefact at the window's trailing edge is regenerated every time. The trailing edge is the newest data, which is exactly what a real-time detector cares most about. Second, filtfilt on a 4th-order Butterworth yields an effective 8th-order magnitude response, so the actual band edges are sharper than the nominal design — worth stating precisely if the filter order appears in the paper.

Recommended direction. Either switch to a stateful causal sosfilt with retained zi (correct for streaming, at the cost of a known phase delay that can be compensated), or keep filtfilt but extract features from the window's centre rather than its edge, accepting a half-window latency. Both are defensible; the current arrangement gets the drawbacks of both.

P1-10 Packet timestamps wrap every 71.6 minutes with no host-side unwrap

parksense_ble_stream_v4.ino:41, 312 · runtime_v2.py:42, 201–204

packet.header.timestamp_us is a uint32_t filled from micros(). It overflows at 2³² µs = 4,294.97 s = 71 minutes 35 seconds. The host unpacks it as "I" and does straightforward arithmetic:

timestamp_us = packet_timestamp_us + i * SAMPLE_PERIOD_US   # runtime_v2.py:201

There is no wrap detection. Over the ~100-hour continuous session the README targets, the counter wraps 84 times, and every wrap writes a ~4,295-second backwards jump into sample_timestamp_us in the CSV. The dashboard's rolling 60-second window is computed from this column, and so is any downstream analysis of a long capture — which is precisely the use case a longitudinal monitoring platform exists to serve.

A related, smaller point: the timestamp is captured once per batch at batchIndex == 0, and per-sample times are reconstructed as nominal multiples of SAMPLE_PERIOD_US. Because the catch-up scheduler at line 294 can advance lastSampleUs by several intervals at once, the reconstructed times are the schedule's intent, not the acquisition's reality. For a platform that claims temporally aligned multi-modal data, that distinction is worth documenting.

Recommended direction. Track wraps host-side with a 64-bit accumulator (detect when the new value is less than the previous and add 2³²), or promote the header field to 64-bit and bump the packet version — the versioned header exists for exactly this. Since the header already has two reserved bytes, extending it is cheap.

P1-11 The test suite contains no assertions and CI cannot run it

tests/*.py (all six files) · .github/workflows/python-app.yml:26–39

All six files under tests/ are print-scripts. A search for assert across the directory returns zero occurrences. test_state_machine.py feeds eleven scores through the state machine and prints the result; nothing checks the result. The files execute at pytest collection time, so they function as accidental import smoke-tests, but no behavioural regression can ever fail them.

The CI workflow compounds this. It runs pip install -r requirements.txt guarded by if [ -f requirements.txt ] — and no requirements.txt exists in the repository, so numpy and scipy are never installed and every test module fails at import. Separately, pytest exits with code 5 when it collects no test functions, which fails the job. Either way the workflow provides no verification.

Coverage is inverted relative to risk. The 2,842-line ppg/algorithms.py — by far the largest, most numerically delicate module — has no test file at all, as do step_counter.py, ppg_processor.py, motion_context.py, multiaxis_detector.py and feature_extractor.py. The one module with a dedicated test, temporal.py, is dead code.

Recommended direction. Add requirements.txt and convert the six scripts into def test_*() functions with assertions. Then prioritise synthetic-signal tests over unit tests of internals: feed a known 5 Hz sinusoid at known amplitude and assert the detector's reported frequency and score; feed a synthetic PPG waveform at a known BPM and assert the estimate. Those tests would have caught P0-2 immediately, and they are the tests a reviewer would want to see referenced in a validation section.

FindingLocationDetail and suggested direction
The 50 Hz notch filter is unnecessary and numerically fragilenotch.py:21–25
motion_pipeline.py:42		Three reasons to remove it. (a) It is applied only to gyroscope data — a battery-powered MEMS sensor with no galvanic path to mains cannot pick up 50 Hz hum. (b) It runs before a 3–8 Hz band-pass that already attenuates 50 Hz by well over 100 dB, so it removes nothing the next stage would not. (c) At fs=104 the Nyquist is 52 Hz, so a 50 Hz notch sits at 0.96×Nyquist where the bilinear transform's frequency warping is extreme and the ba coefficients are ill-conditioned. Deleting it removes a filter pass per axis per call and one paragraph of unsupportable claim from the paper.
Gravity filter uses ba form at a very low normalised frequencygravity.py:18–22Wn = 0.3/52 = 0.00577. SciPy's own documentation warns that transfer-function output is numerically unstable for low-frequency designs and recommends output='sos'. At order 2 this is borderline rather than broken, but it is free to fix: butter(2, Wn, 'low', output='sos') with sosfiltfilt.
Reported frequency precision exceeds spectral resolution by ~40×feature_extractor.py:57–67
runtime_v2.py:276–281		Welch with nperseg=256 at fs=104 gives bin spacing 0.406 Hz, so dominant_frequency can only take values 0, 0.406, 0.813, … The runtime rounds it to two decimals and the README's sample output shows 5.18 Hz — a value the estimator cannot produce. Either report to one decimal with the resolution stated, or add quadratic peak interpolation and earn the precision.
dominant_frequency is a global argmax, not band-constrainedfeature_extractor.py:63np.argmax(psd) searches the entire spectrum including the DC bin. The band-pass suppresses out-of-band content so this rarely bites, but on a low-amplitude window residual leakage can win. Restrict the search to the tremor band, which is what the value is used for.
Spectral entropy is unnormalised and window-size dependentfeature_extractor.py:106–110scipy.stats.entropy returns nats over however many bins exist, so the value is not comparable across window lengths or sample rates and has no interpretable scale. Divide by log(N_bins) for a 0–1 measure — note that algorithms.py:798–801 already does exactly this correctly, so the two modules disagree on the definition of the same feature.
peak_prominence is not a prominencefeature_extractor.py:128–142find_peaks is called and its properties dict discarded (peaks, _ = ...); the field is then filled with np.max(psd[peaks]) — the tallest peak's height. Prominence and height are different quantities. Either request prominence= from find_peaks and use the returned values, or rename the field to max_peak_power.
Motion context takes the magnitude of already-gravity-removed axesmotion_pipeline.py:60–68
motion_context.py:25–33		Each axis is gravity-removed, then the vector magnitude is taken, then the mean is subtracted. Because √(x²+y²+z²) of zero-mean signals is strictly non-negative, this is a rectification followed by a de-mean — a nonlinear operation that folds negative excursions and roughly halves effective sensitivity. The conventional formulation computes the magnitude of the raw accelerometer vector and then removes the 1 g baseline. The thresholds 0.03/0.20 g were presumably tuned against the current behaviour, so changing this requires re-tuning them.
Confidence re-scores the same three inputs as the scoreconfidence.py:11–73
multiaxis_detector.py:77–96		ConfidenceEstimator consumes frequency_std, band_ratio and axis_agreement — the identical features the score is built from. It is therefore a monotone re-expression of the score, not independent evidence, and can never meaningfully disagree with it. Most importantly it ignores amplitude entirely: a 0.81 dps tremor scraping past the gate and a 40 dps tremor receive the same confidence. Amplitude relative to the noise floor is the single most informative confidence input available and it is unused.
Score is a sum of binary thresholds with cliff-edge behaviourmultiaxis_detector.py:77–9635 + 30 + 20 + 20 with a detection bar of 80 means tremor requires the frequency gate and the band-ratio gate and at least one of agreement/dominance — an AND of three conditions expressed as arithmetic. A band ratio of 0.1799 versus 0.1801 swings the score by 30 points. Graded membership functions (sigmoid or trapezoidal) over the same features would give a continuous, far more stable score with no change to the feature set, and would read considerably better in a paper than four hard-coded integers.
The detector's own confidence computation is deadmultiaxis_detector.py:116–118
rule_engine.py:47		confidence = int(score * axis_agreement) is computed and returned, then unconditionally overwritten one call up the stack. Delete it.
rest_index is duplicated verbatimmultiaxis_detector.py:71–74, 146–149The same expression appears in both the early-return and normal-return dicts. Two places to forget when the 0.20 constant changes.
Confidence penalties are applied after the clampconfidence.py:55–71The value is clamped to 100 and only then multiplied by the 0.5 penalties, so a raw 120 and a raw 200 both become 50. Not a correctness bug, but the ordering makes the penalty non-monotonic in the underlying evidence.

8.2 Terminology and framing

  • "Digital biomarker" is used for every output including step count and distance. In the neurology literature the term carries a connotation of validation against a clinical endpoint. Consider "derived metrics" for the activity channel and reserving "candidate digital biomarker" for the tremor measures.
  • "Tremor Burden" appears in the biomarker table and the pipeline description but no module computes it — there is no burden accumulator in the live path. Either implement it or remove it.
  • "Severity" categories (NONE / VERY MILD / MILD / MODERATE / HIGH / SEVERE) are thresholds on an unvalidated composite score. Because those words map onto UPDRS-style clinical vocabulary, a reviewer will read them as claiming correspondence with clinical severity. Neutral labels — or an explicit "score band, not a clinical severity rating" note — would avoid the inference.
  • "~104 Hz" versus "104 Hz" is used inconsistently for the same quantity. Pick one and state the measured jitter.
  • Missing citations. Several well-established choices are presented as bare constants: the 4–6 Hz Parkinsonian rest-tremor band, the 0.25 ratio for the AC/DC perfusion bound, the 20% ectopic-beat threshold, Elgendi's one-third systolic upstroke ratio (cited in a comment at algorithms.py:186 but not in the README). Citing these strengthens the work considerably and costs a paragraph.
  • The comparison table framing is good. The "architectural comparison, not a performance claim" sentence is the right instinct and should be kept verbatim — it pre-empts the most obvious reviewer objection.

10. Closing Assessment

ParkinSense is a stronger piece of work than this report's length suggests. An audit finds problems by construction; it does not weigh them against what went right. So to be explicit about what went right: the module decomposition is genuinely good, the PPG algorithm file is careful and literature-aware in a way that is rare in a project this size, the step counter is well-built and honestly documented, decoupling the dashboard from the runtime through files was the correct architectural call, and the README's willingness to state its own limitations plainly is a real asset.

The central problem is a gap between the designed system and the running system. Sophisticated components were written, and then either not wired in, or wired in under conditions that break their assumptions — a per-sample loop where a per-window loop was intended, a default sample rate that nobody overrode, a settings struct populated one line too late. These are integration defects, not design defects, which is why the fix list is short relative to the finding list.

On priorities: the single most useful thing would be to verify P0-2 with the two-minute debug check before touching anything else. If heart rate is indeed returning None for the reason predicted, that one finding explains an entire troubleshooting section of the README and unblocks four biomarkers. Items 1–4 together are perhaps a day of work and change the system from "produces plausible-looking numbers" to "produces numbers you can defend."

On the research direction ChatGPT proposed — personalised models, bradykinesia and dyskinesia indices, validation against published datasets — that assessment is right about where the ceiling is, but the sequencing should be inverted. Adaptive and personalised models trained on a signal chain with an unapplied gyroscope range, an aliased PPG stream, and a temporal validator that never runs would learn those artefacts. Fix the measurement chain first; then the algorithmic ambition has something trustworthy to build on. The instinct to compare the tremor detector against TremoSense, PKG and KinesiaU is a good one — but the comparison only means something once you can state, with test coverage behind it, what your own detector actually does.
